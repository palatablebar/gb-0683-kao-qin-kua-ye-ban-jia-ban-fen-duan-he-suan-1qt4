# 审批额度落段裁决（RATE_FIRST）

## 裁决结论

夜班跨节假日被切成不同倍率片段，而月底审批单只写「员工 + 总分钟」、不指定片段。
两种朴素做法：

- 先到先得（按发生先后）：保住同班时间线，却可能让高倍率工时无审批、无法支付，员工损失最大；
- 高倍率优先：审批依据的落段次序与发生先后不一致，但在相同额度下使可支付金额最大、员工损失最小。

**本项目采用高倍率优先（RATE_FIRST）**。理由：审批单的约束对象是员工的加班总量而非片段，
额度本身对片段无偏好；在额度受限（审批分钟 < 实际加班分钟）时，优先覆盖高倍率片段是使员工
损失最小的唯一确定性规则。次序与时间线不一致的问题，通过逐段留痕（依据单号、落段次序、
策略名）解决，而不是通过牺牲可支付性解决。

## 确定性算法

1. 解析审批单（JSON 列表或 `order_id,employee,approved_minutes` CSV），按员工汇总额度。
   - 分钟必须为非负整数；同一 `order_id` 重复出现按重复单据隔离，不静默覆盖；
   - 单据对应员工在本批没有任何有效加班片段的，记 `APPROVAL_UNMATCHED` 异常，额度不耗用、不挪用；
   - 员工有加班但无审批单的，额度为 0，全部计入未批。
2. 取该员工全部计费片段，按 `(倍率 DESC, 起始时刻 ASC, 段序 ASC)` 排序。
3. 用员工额度按顺序消耗：片段得 `approved_minutes = min(剩余额度, 片段分钟)`，
   `unapproved_minutes = 实际分钟 - 已批分钟`，并记录 `allocation_rank` 与来源审批单号。
4. 额度大于全部实际分钟的余量记为员工级 `unused_approval_minutes`（批而未用）。
5. 金额按片段 Decimal 计算：`金额 = 时薪 × 分钟 × 倍率 / 60`，四舍五入到分；
   `应付 = round(全额 × 已批 / 实际)`，`不付 = 全额 - 应付`，保证分币守恒。

## 逐项对应关系（可付款结果）

每个计费片段一行：

| 字段 | 含义 |
|---|---|
| minutes | 实际加班分钟 |
| approved_minutes | 已批分钟（本片段落段） |
| unapproved_minutes | 未批分钟 = minutes − approved_minutes |
| amount | 全额应付（整段按倍率折算） |
| payable | 实际可付（仅已批分钟，到分） |
| withheld | 不付金额（未批分钟，到分） |
| multiplier / code | 倍率与分类（HOLIDAY/REST/OVERTIME/REGULAR） |
| allocation_policy / allocation_rank / order_ids | 裁决留痕 |

员工汇总（approval_ledger）：实际分钟、审批额度、已批、未批、批而未用、应付、不付。

## 失效、幂等与发布

- 运行幂等键 = 打卡字节 + 参数（含审批单）+ 规则版本的哈希；审批或打卡一更新，新 run 产生，
  旧 run 整份保留并由同 scope 的更新批次标记 `superseded`，不删记录。
- 同输入重复提交命中同一 run_id，`INSERT OR IGNORE`，审批额度不会被重复耗用。
- 封存为单数据库事务：写封存标记失败则整体回滚，旧封存版本与原始依据（source_b64）保留。
- 对账新增两道守恒：分钟守恒（实际=已批+未批；已批=min(额度,实际)）与应付独立求和；
  任一对账不平，`balanced=false`，禁止封存、禁止导出。
- 页面与 CSV 导出读取同一份 run 结果，不允许各自重算。
